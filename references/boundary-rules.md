# 工具与执行职责检查

按 `skill-standard.md` 先看实际用途与影响。以下是设计线索，不是互斥分类或强制架构。

| 部分 | 常见职责 | 何时需要检查 |
|---|---|---|
| Skill | 供 Agent 选择与使用的指令、判断依据、资源 | 所有目标 |
| Agent | 理解任务、选择工具、处理非结构化信息 | 流程依赖判断时 |
| 工具 / script | 确定性计算、转换、外部操作 | 反复易错或有真实执行步骤时 |
| workflow / 宿主 | 状态、重试、长流程协调 | 承诺可靠重试、断点续跑等机制时 |
| cron / scheduler | 定时或事件驱动运行 | 声称无人值守或定时执行时 |
| MCP / API / CLI | 暴露外部能力的接口 | 依赖外部系统时 |

检查时回答：
1. 谁调用或触发？若由现有平台负责，Skill 可以只引用该机制，不必自建调度器。
2. 哪些动作需要判断，哪些操作重复且容易出错？是否已有可靠工具，是否值得封装脚本？
3. 有何外部副作用？必要范围、授权、重复执行后果是否清楚？
4. 失败需要解释、停止还是重试？相应机制能否由已知宿主提供？

只报告有证据的职责缺口：
- 声称每天自动执行，却没有运行宿主或调度说明 → 明确可用的触发机制或收窄承诺。
- 关键操作需要反复现场拼复杂请求且有已知易错参数 → 固化参数校验或可靠工具入口。
- 写操作会在重试时重复产生不可接受结果 → 给出停止、去重或适合该操作的恢复方式。
- 必需工具不明 → 补接口、最低环境和失败信号；当前工具是否已安装未知时记待确认。

不要因为输入是 JSON 就禁止 Agent 阅读；不要因为有多个固定步骤就强制搭建 workflow。安全、可靠且足够简单的现有平台能力可以直接使用。

调用控制、动态资源、子 Agent 或新工具能力由实际宿主定义；不因旧分类表没有列出就否决。用 `platform-adaptation.md` 核对适用环境，接受满足同一要求的原生能力；不要要求已有宿主提供的机制再造一遍。

报告只需写明相关边界问题的“条件 → 事实 → 影响 → 最小修复”。没有涉及的组件记不适用，不输出空泛的架构升级建议。
