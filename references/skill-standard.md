# 本项目 Skill 审查规则 v0.4

这是 skill-auditor 的审查约定，供通用质量体检使用，不是行业标准或平台认证。目标平台的明确要求、用户用途与可核查证据优先于结构偏好。

## 1. 审查对象与上下文

Skill 是供 Agent 使用的可复用指令及其必要资源。单文件可以充分，目录齐全也可以无法使用。

稳定检查关注任务能否被理解、执行与验收；平台语法、工具名称、模型能力和版本限制在审查时核实。不同格式、显式调用、运行时注入资源或新字段不自动构成缺陷；具体方法见 `platform-adaptation.md`。

先记录以下上下文；能从目标文件和用户请求推断的注明推断，未知的保留为未知：
- 用途：帮助完成什么任务，什么情况不适用？
- 使用者：作者本人、团队还是对外提供？是否能依赖个人背景知识？
- 环境：目标 Agent / 平台、工具、文件和外部服务是什么？
- 结果：交付什么，错误或重复执行的后果是什么？

只问会实质改变审查结论的问题。没有用户回复时，继续独立可做的审查；不把未知当缺陷，也不根据目录反推受众或交付档位。

## 2. 五项通用质量

| 维度 | 核心问题 | 可接受的证据 |
|---|---|---|
| 选择与边界 | 能否判断何时使用及能力范围？ | description 与正文清楚限定任务；无需固定触发语数量 |
| 执行指导 | 新使用者能否据此决定动作与分支？ | 明确动作，或足够具体的目标、约束和判断依据；无需编号步骤 |
| 输出与验收 | 能否知道做完应是什么样？ | 输出格式、质量要求、示例或适合任务的检查方法；无需独立 tests/ |
| 一致性与资源 | 指令是否冲突，必要资料能否找到？ | 规则与示例一致，资源可达，指代可理解 |
| 依赖与异常 | 必要环境、缺信息和失败的处理是否足够？ | 与实际依赖、使用后果相称的说明；无需对无副作用任务要求回滚 |

每个维度记录“通过 / 有问题 / 不适用 / 待确认”，并列出证据。维度中包含多项检查时分别记录；存在已确认问题就标“有问题”并保留其他未知，只有必要项均有依据才标“通过”。
- 通过：已检查内容足以支持当前用途下的判断；注明静态或行为证据。
- 有问题：有证据表明特定情形下会产生错误、阻塞、歧义或可解释的维护成本。
- 不适用：该要求在当前用途没有实际必要性，说明理由。
- 待确认：材料或环境不足，说明缺什么及如何确认。

无总分、分母、及格线或按目录推断的成熟档位。若用户另有评分规范，单独说明规则和适用范围，不把自定义分数解释为通用质量认证。

## 3. 场景检查按条件启用

| 场景 | 需要额外核对 | 不能据此强制要求 |
|---|---|---|
| 写作、创作、知识指导 | 受众、风格或判断依据、输出要求、缺背景时的处理 | 必须有脚本、自动化测试或唯一答案 |
| 工具调用、代码或数据处理 | 必要参数、依赖、成功与失败信号；易错重复操作是否有可靠执行方式 | 每条命令都封装脚本、所有 JSON 都禁止 Agent 阅读 |
| 写文件、发送、发布等副作用 | 范围与授权、重复执行的后果，必要时的预览、去重或恢复 | 纯只读任务必须有事务、回滚或审批流 |
| 长期共享、外部 API 依赖 | 可迁移的环境说明、版本或来源、接口变化后的更新方式 | 所有个人 Skill 必须有 CHANGELOG 或七层目录 |
| 特定平台 Skill | 核对用户提供或可取得的该平台明确要求 | 把一个平台的命名、元数据限制推广到所有平台 |

不要预先建立穷尽所有领域的检查表。领域准确性需要来源、专业依据或实际测试；缺少它们时将这一项列为未验证。

## 4. 问题证据与优先级

每个问题包含：位置（文件与行号或章节）、适用情形、观察到的事实、对用户的影响、最小修复。建议有收益而无法证明当前存在问题时，单列“可选建议”。

- P1：有证据的阻塞或重大错误，例如必经资源不存在、核心指令互相冲突而无法确定执行方式、明确的非授权副作用。
- P2：常见情形下的不稳定、歧义或环境缺口，有明确修复价值但不阻塞所有使用。
- P3：影响较小的可读性、维护或效率问题，需说明实际成本。

优先级按具体影响判断，不由反模式编号固定决定。同一根因只报告一次。不凑问题数量，不因模板有某栏而要求目标 Skill 增加文件。

## 5. 总体结论与覆盖范围

先固定结论覆盖的用途：用户指定时按指定用途，未指定时按 Skill 声明的主用途。可执行的降级分支单独评价，不用它替代尚无依据的主用途结论。例如缺少设施专用规范时，主用途可以是“信息不足”，而“索取规范并提供通用解释”的降级指导可以足够清楚。

按下列顺序选择结论：
1. 有已确认 P1 → **需先修复**；未知项另外保留。
2. 无 P1，但用途、必需资源或环境等关键未知阻碍整体判断 → **信息不足**；写出能独立确认的其他问题。
3. 其余 → **暂可用**；注明用途、静态审查范围与 P2/P3 缺口。非关键的未知不会自动否决，但必须列出。

不使用“Skill 不成立”“成熟”或“认证通过”作通用结论。暂可用不等于功能已验证。只有实际执行了测试，才能声称行为通过。

## 6. 自动盘点与人工判断

`../scripts/check_structure.py` 输出 v2 JSON：
- `skill_md`：存在性、行数、name/description 元数据，以及格式错误；解析失败的正文仍可人工审查。
- `directories`：常见资源目录的文件盘点，目录缺失只是事实。
- `ghost_references`：扫描范围内本地相对引用不存在的候选清单；示例路径也可能被收录，需人工核实用途。
- `unlinked_files`：扫描到的文档中没有发现引用的常见资源文件。目录级引用算已覆盖，不据此认定资源无用。
- `external_references`：绝对路径、URL 或越出目标根目录的引用，不检查可达性。
- `deferred_references`：运行时变量、注入命令或路径模式，未展开或执行，不视为文件缺失。
- `ambiguous_references`：不同基准下均存在的候选路径；未擅自选择或递归读取。
- `skill_md.frontmatter_keys`：实际元数据字段名，保留未知扩展，不按固定白名单判错。
- `scanned_documents`、`warnings`：实际读取范围、元数据和读取问题。

路径默认同时考虑文档目录与 Skill 根目录，也可用 `--path-base skill` 或 `--path-base document` 指定已核实的基准；候选存在不代表宿主一定采用该解释。目录输入从入口递归读取已引用的本地 Markdown 文件；单文件输入只读取该文件、核对其本地路径，不盘点或递归读取其他资源。两者在报告里分别说明覆盖范围。

脚本只读文件，不加载目标代码、不联网、不检查章节锚点是否存在。正文中没有反引号或链接标记的裸路径、完整命令行参数、跨目录链接、动态路径和复杂 Markdown 语法需要人工复核；空缺清单不能证明引用完全有效。

## 7. 验证与维护

修改审查规则时同步入口、清单、模板和案例；修改盘点脚本时运行回归测试。重点验证：简单 Skill 不因缺目录被批评，有缺陷的复杂 Skill 不因目录齐全被放行，同一问题能给出稳定证据。

默认给用户短报告：能否用于指定任务、主要问题与最小修复、实质影响结论的未知。每条问题保留可核查位置，但不默认倾倒评分表、分类编号或实现术语。完整覆盖表供需要详细报告时使用。

遇到新能力时先按现有质量目标和宿主约定判断；只有真实错误或误判才推动规则修改，不为猜测的未来功能预设插件、适配器或限制。审查不会自行修改本 Skill，也不承诺固定年限内永远正确。

本项目用 Python 3.10+ 与 PyYAML 6.x；仅本地读取和 stdout 输出，不需要凭证。安装、测试与使用见 `../README.md`。版本历史见 `../CHANGELOG.md`。

七层模型保留为可选的问题定位视角，见 `checklist-7-layers.md`；它不参与默认评分和通过判定。
